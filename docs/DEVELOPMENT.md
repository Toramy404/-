# 开发与维护

这是一款个人维护的离线工具，采用一条稳定主线加短期分支。无需建立复杂团队流程，也无需每次调整都安装手机包。

## 每次改动的固定顺序

1. **记需求。** 功能异常、数据纠错、功能建议分别用仓库 Issue 表单。写清楚现在的问题、希望怎么用、什么结果算完成；小文案修正可直接在 PR 中说明。
2. **开分支。** 从最新 `main` 建立 `fix/问题名`、`feat/功能名`、`data/数据主题` 或 `chore/维护主题`，一次只处理一件相关事情。
3. **修改和预览。** 运行 `npm start`，电脑直接看效果。涉及布局时检查正常桌面和约390px手机宽度；需要用户确认的体验在这一步确认。
4. **检查。** 运行下方命令；涉及资料时按 DATA.md 补来源。测试不通过就先修，不把失败写成“已完成”。
5. **提交 PR。** 写问题、结果、检查情况和未测部分。自动检查为绿且人工看过后，以 Squash merge 合入 `main`。提交标题建议 `feat: …`、`fix: …`、`data: …`、`docs: …`、`chore: …`。
6. **按需发版。** 用户确认要装手机、修复影响使用的问题，或积累了完整一组改动时才构建正式 APK。完成手机检查后创建版本标签与 Release，附安装包、SHA-256 和更新说明。

这沿用 [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)。`main` 表示可继续开发的稳定源码，正式发版由标签和 Release 标记；还没发版的内容写入 CHANGELOG 的 Unreleased。

## 本地最少命令

```sh
npm start
npm run check
npm test
python scripts/build_data.py --check
```

检查包括脚本语法、版本一致、离线资源完整、已跟踪文件中的私钥/令牌特征、词条覆盖与引用、档位规则、历史/收藏兼容和父级返回。测试用例中的固定数量属于当前数据基线，正式增加数据时应连同来源和预期数量一起审查，不能只为通过测试随意改断言。

`dist/` 是本项目真实网页源码，不是可以全部删除重建的普通前端输出目录。`data.js` 单独由数据生成脚本维护，其他 HTML/CSS/JS 在此编辑。旧的 v0.3 手机网页 ZIP 脚本已停止继续打包；电脑预览和 Android 构建是当前维护入口。

## 版本号与发版

采用 `主版本.功能版本.修订号`：小问题修复如 0.4.1，成组新增功能如 0.5.0。公开接口或存档不兼容的大变化再考虑主版本升级。每次 APK 升级都要增加 Android `versionCode`；不得更换 `local.duye.nightreign` 包名和既有签名。

同时更新 `android/AndroidManifest.xml` 的 versionName/versionCode 与 `package.json` 的 version，补 CHANGELOG。数据快照版本在 `data/meta.json` 独立维护，不随纯界面更新虚增。网页缓存内容变化时更新 `dist/sw.js` 的 CACHE。

签名构建详见 [Android 构建](../android/README.md)。发布前需要：

- 检查 PR 自动检查、电脑与手机宽度预览。
- 手机保留旧版记录，直接覆盖安装；确认收藏、水晶标记、设置仍在。
- 飞行模式冷启动，查询词条、夜王和地图；确认本地图片完整。
- 原记录→档位表→栏目→首页逐级返回；首页系统返回与页面返回均能退出。
- 清除最近查看并撤销；导出记录并在文件管理器确认 JSON 已保存。
- 核对 APK 的包名、版本、签名、SHA-256，填写实际设备/Android版本/结果。

测试结果写在 Release 说明或对应 PR 中即可，不另建重复台账。未经真机验证的包标明“测试版”。已发布 APK 不覆盖，不用同一个版本号发不同内容。

通过 GitHub Releases 页面选择已验证的 `main` 提交，创建 `v0.4.1` 等标签，附 APK 和校验值。不要将 APK 放进源代码提交。当前连接的 GitHub 工具能维护代码、PR、Issue，但没有修改仓库设置或上传 Release 附件的接口；这两个入口可在网页完成，不能把未完成的设置称为已经启用。

## 出问题怎么回退

优先撤销出问题的提交，在新分支上修复并重新验收。手机侧保留同一签名，以更高 versionCode 发布回退内容；不要强行降级或先卸载，避免丢失个人记录。源码可回退不等于手机存档迁移一定可逆，涉及存储结构时先导出记录，并测试旧存档兼容。

## 保管与仓库设置

`android/signing/` 存放现有私钥与密码，仅留本机，另在用户自己控制的加密备份中保留。不要把它发到 Issue、聊天、公开仓库或普通 ZIP。Git 忽略文件不是密钥备份；丢失密钥会影响覆盖升级。

建议仓库 Settings → Rules → Rulesets 对 main 要求 PR 和通过 `Data and behavior`、`Android compile` 两项检查，禁止强推和删除主分支。个人维护者可不要求第二人批准，避免自己无法合并。这是建议配置，需按 Settings 中实际启用状态核实。

仓库现在的技术名称是 `-`。显示标题使用“渡夜手册”；若之后改为 `duye-handbook`，同时更新本地 origin、README 中的链接和后续下载链接。

每月处理一次依赖更新 PR；遇到游戏更新优先检查数据版本、来源差异和相关 Issue。每次发版检查签名备份可用，但不把备份内容放进仓库。先解决崩溃/数据错误，再做影响查询效率的体验，最后处理装饰。
